# UI設計の共通ルール

画面を増やす・直すときの共通判断基準。**最小表示・余白・操作の明快さ**を優先する。画面固有の機能・寸法・色・演出は各プロジェクトの仕様を正とし、この文書には複製しない。

## 1. 表示する前に選別する

画面の目的と主な操作を定め、表示候補を次の3つに分けてから構成する。

- **常時必要**：その画面で今判断・操作するために欠かせない情報。
- **操作・選択時のみ必要**：対象を選ぶ、詳細を見る、失敗するなど、必要になったときだけ出す情報。
- **不要**：重複した見出し、一般的な仕様の説明、内部処理・開発都合・AIによる補足、用途が薄い項目。

まず最小の構成を作り、操作できない・誤解する箇所に限って情報を戻す。既に表示されているからという理由だけで残さない。小規模な文言修正で大げさな棚卸し文書を作る必要はないが、この分類による判断は省略しない。

## 2. 余白は設計要件

- 空いているから埋めない。削って生まれた余白を別の説明・カード・装飾で埋め戻さない。
- 情報過多を、小さな文字、詰めた余白、追加の枠・見出し、安易な折りたたみで解決しない。
- 文字・視覚的階層・配置で主な操作を目立たせ、すべてを強調しない。色や動きだけで意味を伝えない。
- 製品の世界観・遊びの体験を担う表現は、単なる説明文と区別する。ただし、その理由で画面を埋め尽くさない。

## 3. 操作と状態は短く明確に

- まず配置、操作そのもの、状態の変化、操作結果で伝える。説明が不可欠なときだけ、その場所に短く示す。大量の補足をヘルプへ移すだけで解決としない。
- 意味が明確な状態はアイコンやゲージを優先する（例：「ロック中」→鍵）。一方、意味が曖昧な主要操作は短い文字ラベルを残す。「何でもアイコン化」はしない。
- アイコンだけの操作にはアクセシブルな名前を付け、キーボード・タッチ・読み上げでも理解・操作できるようにする。スマホでホバー説明だけに依存しない。
- 誤操作防止、公開範囲、同意、重大な制約、破壊的操作の確認、失敗からの回復に必要な情報は削らない。必要な時点で最小限に伝える。
- 同じ役割には同じラベル・アイコン・位置・挙動・余白と既存の共通部品を用いる。見た目を揃えるために異なる役割まで同一化しない。表示が切り替わってもフォーカスや入力を不用意に失わせない。

## 4. 増える一覧は取得と表示を分ける

データが増える一覧は、取得上限・並び順・ページング・検索範囲・失敗時の挙動を先に決める。全件取得して画面内だけで分割しない。部分取得なら件数・検索・集計がどの範囲を示すか誤認させない。件数が固定で小さい場合は一括取得も選んでよい。すべての画面に同じ検索やページングを強制しない。

## 5. 画面全体で確認する

UIを変更するときは、変更した部品だけではなく**画面全体**を確認する。

1. 常時表示・操作時表示・不要な情報の分類は妥当か。重複した文言・見出し・説明・装飾はないか。
2. 主な操作、共通部品、状態・結果、誤操作防止の導線が整っているか。
3. PCとスマホ、狭い画面、長い文字、大きい文字、配色差、キーボード・読み上げで読めて使えるか。
4. 余白を圧縮していないか。削った場所に別の情報を追加していないか。

画面変更前後の実表示・操作を確認し、PRには確認済み事項と未確認事項を短く残す。必要なスクリーンショットやプレビューの保存・共有方法は各プロジェクトの規則に従う。静的チェックやテストに合格しただけで、見た目の確認が済んだとは扱わない。

## 6. 収まらなければ実装を止める

**余白を守りながら必要情報・操作を収められないとき、または重要な情報を削らなければ成立しないときは、そのUIの実装を中断してオーナーへ相談する。**

独断で文字や操作領域を縮め、無理に押し込んだ状態を完成扱いにしない。相談では、衝突している情報・削減候補・判断が必要な点を簡潔に示す。無関係な作業まで止める必要はない。

オーナー向け・開発者向けの画面にも同じ基準を適用する。安全・アクセシビリティ上の例外やプロジェクト固有の制約がある場合は理由を明示し、暗黙に共通原則を上書きしない。

## 採用プロジェクトでの運用

- 各プロジェクトの開発入口（例：`AGENTS.md`）から、このREADMEを**UI作業前の必読資料**として案内する。
- 共通判断の正本はこの公開リポジトリ。画面固有の仕様だけ各プロジェクトに置き、同じ長文をコピーして二重管理しない。
- 外部参照が一時的にできないときのため、**最小表示・余白優先・収まらなければ相談**の停止条件だけは各プロジェクトの入口にも残す。
- 共通ルールを変更するときは採用プロジェクトへの影響を確認する。自動同期や仕組みの追加は、運用上必要になってから検討する。
